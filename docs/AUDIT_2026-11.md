# PeaWork HRMS — Independent Code & Architecture Audit

**Audit date:** 2026-11-17  
**Scope:** `app/` (v1.2.0), `scripts/`, `tests/`, Docker/deployment assets, documentation claims  
**Method:** static review, dependency/runtime checks, baseline test execution, data-model and authorization tracing  
**Auditor note:** this is a technical audit, not a legal, statutory, or certification assessment.

---

## 1. Executive summary

PeaWork v1.2.0 is a **feature-rich functional prototype** with an unusually broad domain footprint (core HR, recruitment, onboarding, workforce, talent, payroll, cloud control plane, privacy/readiness). The breadth is real and the domain modelling shows genuine thought. It is **not** a production-ready HRMS, and it should not be deployed to a Linux server in its current form.

The single largest risk is structural: almost the entire application is **one 1,858-line, ~198 KB FastAPI module** that mixes routing, SQL, business rules, HTML context assembly, authorization, and audit. That makes every change a regression risk and makes security review effectively impossible.

### Readiness scorecard

| Dimension | Score | Verdict |
|---|---:|---|
| Functional breadth | 8/10 | Strong prototype coverage |
| Architecture & maintainability | 2/10 | Monolith with no module boundaries |
| Security & authorization | 3/10 | Good primitives, broken object-level authz |
| Data integrity | 4/10 | Constraints live mostly in application code |
| Test health | 2/10 | 18/28 tests failing at audit time |
| Deployment & operations | 3/10 | Dev server, no TLS/migrations/backups in local path |
| Observability | 3/10 | Health/metrics exist, no structured logs/tracing |
| Documentation honesty | 7/10 | Explicit "candidate, not certified" caveats are good |
| **Overall production readiness** | **2.5/10** | **Do not deploy as-is** |

### Verdict

> Keep v1.2 as the **reference implementation and requirements source**. Build the production system as a modular successor, migrate data, and retire the monolith. Do not attempt a big-bang rewrite of every module at once.

This audit is paired with:
- `docs/ROADMAP.md` — release-by-release remediation and build plan.
- `docs/ARCHITECTURE_V2.md` — target architecture on a Linux host using open-source components.
- The new `peawork/` package — the first working vertical slice of that architecture.

## 2. Baseline evidence

### 2.1 Test execution

```
python -m pytest -q
18 failed, 10 passed
```

Representative failures:
- `test_health` — version assertion expects `1.0.0`, application reports `1.2.0`.
- All authenticated form workflows — HTTP `422` on `POST /login` and every subsequent form POST.

### 2.2 Root cause of the red suite (confirmed)

`app/main.py` lines 25–31:

```python
if request.method not in SAFE_METHODS and request.url.path not in CSRF_EXEMPT:
    submitted = request.headers.get('x-csrf-token')
    if not submitted:
        try:
            submitted = (await request.form()).get('_csrf')
        except Exception:
            submitted = None
```

`security_middleware` is a `BaseHTTPMiddleware`. Reading the form consumes the request stream; Starlette 1.10 then hands the downstream route an empty body. Result: `Form(...)` parameters are missing and FastAPI returns `422`. This breaks login, employee creation, leave, payroll — every state-changing browser flow. It is a **release-blocking functional defect**, and it also proves the deployment cannot be reproduced from the test suite.

**Status:** fixed in this change set by reading/caching `request.body()` and parsing it without consuming the downstream stream. See `app/main.py` remediation.

### 2.3 v2 progress

The modular successor in `peawork/` has reached **R1 vertical slice** status:

- Alembic migrations applied and verified with `alembic check`.
- v2 test suite: **40 passed** (`pytest tests/v2 -q`).
- Full repository suite: **67 passed, 1 known legacy failure** (M-4).
- Live smoke test: health, login, admin, sample data, bulk import and Excel reports.
- New features this change set: 100-employee sample hierarchy with safe
  cleanup, CSV/XLSX bulk import with full rollback, and Excel report exports
  (employee register + nine-sheet workbook).

### 2.3 Dependency reality

- `requirements.txt` pins exact versions (good) but has **no hashes**, no lock file, no SCA step, and no CI.
- `psycopg[binary]` bundles a binary wheel; acceptable, but should be a deliberate choice for the target distro.
- `pytest` is in production requirements (should be a dev extra).
- No separate dev/prod dependency sets; the production image installs the test stack.

## 3. Findings

Severity: **Critical** = exploitable or data-loss; **High** = production blocker; **Medium** = material risk; **Low** = hygiene.

### C-1 — Broken object-level authorization (IDOR) in core workflows
**Severity: Critical**  
**Evidence:** `app/main.py:234` (`leave_request`) accepts `employee_id` from the form with no ownership check. Any authenticated employee can file leave for any other employee. `app/main.py:239` (`leave_decision`) allows any `admin`/`hr`/`manager` to approve **any** leave request, not just their reports. Similar patterns exist across attendance, timesheets, documents, profile changes, and self-service.

**Impact:** horizontal privilege escalation, falsified leave/attendance/payroll inputs, privacy breach.  
**Remediation:** central authorization policy (`can(user, action, resource)`), employee-scope resolver, manager-of relationship checks, deny-by-default, and tests for every role × resource pair. This is a **must-fix before any pilot**.

### C-2 — CSRF middleware breaks all form writes
**Severity: Critical (functional)**  
**Evidence:** above; confirmed by baseline suite.  
**Status:** fixed in this change set.

### H-1 — Monolithic application module
**Severity: High**  
**Evidence:** `app/main.py` = 1,858 lines / 197.9 KB; multiple statements per line; no service or repository layer; every route builds SQL and HTML context inline. `app/db.py` = 530 lines of schema DDL plus a custom `PgConnection` shim that rewrites SQL and appends `RETURNING id` by string inspection.

**Impact:** unmaintainable, untestable in isolation, high regression rate, impossible to reason about transactions, dangerous adapter (string-rewriting SQL).  
**Remediation:** modular package, SQLAlchemy 2.0 ORM, Alembic migrations, routers/services/repositories, typed settings, no SQL string rewriting.

### H-2 — No migration framework
**Severity: High**  
**Evidence:** `init_db()` uses `CREATE TABLE IF NOT EXISTS` only; no `ALTER TABLE` path in `app/db.py`. Schema evolution relies on fresh databases.  
**Impact:** any upgrade of a live installation risks data loss or silent divergence between SQLite and PostgreSQL.  
**Remediation:** Alembic, versioned revisions, upgrade/downgrade tests, forward-only production policy.

### H-3 — SQLite default for a multi-user server
**Severity: High**  
**Evidence:** `DEFAULT_DB` is a local SQLite file (`app/db.py:6`); local Docker compose has no PostgreSQL; PostgreSQL is opt-in via env var.  
**Impact:** write locking, corruption risk under concurrent writes, weak backup/PITR story, no row-level security.  
**Remediation:** PostgreSQL 16 as the only supported production database; SQLite permitted for tests/dev only.

### H-4 — Role-only authorization, no data scoping
**Severity: High**  
**Evidence:** `require(request, roles)` is the entire authorization model (`app/main.py:92`). APIs such as `GET /api/v1/employees`, `/api/v1/leave-requests`, `/api/v1/payroll-runs` return broad datasets to any holder of a role. `app/main.py:242` exposes all documents to any authenticated user.  
**Impact:** over-exposure of PII and compensation data; insider risk.  
**Remediation:** policy engine with object-level and field-level rules (self / manager / HRBP-by-department / payroll / auditor), response filtering, and audit of access to sensitive records.

### H-5 — Home-grown session and crypto code
**Severity: High**  
**Evidence:** `app/security.py` implements HMAC-signed base64 tokens, custom CSRF tokens, and a PBKDF2 scheme. Session registry lives in a **separate control database** (`app/cloud_control.py`) even for single-tenant use. No rotation on privilege change, no idle timeout, no device/session management UI.  
**Impact:** subtle cryptographic and lifecycle bugs; cross-database consistency failure modes (session revoked in control DB but app DB transaction still commits).  
**Remediation:** opaque random session tokens, hashed at rest, stored in the primary database, rotated on login/privilege change, idle + absolute expiry, "sign out all devices"; Argon2id passwords.

### H-6 — Tenant selection from client-controlled input
**Severity: High**  
**Evidence:** tenant context middleware reads `peawork_tenant` cookie **or `x-peawork-tenant` header** (`app/main.py:42`), then resolves via `resolve_tenant`. Session is bound to tenant, which limits replay, but tenant selection itself is client-controlled and PostgreSQL schema names are derived from a regex sanitizer (`app/db.py:52`).  
**Impact:** tenant-confusion bugs, cross-tenant data exposure if the session/tenant binding check is ever bypassed; `search_path`-based isolation is fragile.  
**Remediation:** for self-hosted v2, one organization per deployment (no tenant switch). For SaaS, resolve tenant from verified host/IdP claim, never from a client cookie/header, and use database-per-tenant or RLS.

### H-7 — Default secrets and permissive startup
**Severity: High**  
**Evidence:** `PEAWORK_SECRET` defaults to `dev-only-change-me`; bootstrap admin defaults to `ChangeMe123!`; startup refusal only applies when `PEAWORK_ENV` starts with `cloud`/`production` (`app/main.py:101-109`). A Linux operator who forgets `PEAWORK_ENV` runs with known credentials.  
**Remediation:** fail-closed by default, generated secrets on first boot with one-time display, forced password change, refuse demo credentials outside explicit `dev` mode.

### H-8 — Money stored and computed as floating point
**Severity: High (financial)**  
**Evidence:** payroll tables use `REAL` for salaries/amounts (`app/db.py:297,313,319,325,334`); `money()` converts via `Decimal(str(...))` per operation but persists floats.  
**Impact:** cumulative rounding drift, reconciliation failures, statutory reporting errors.  
**Remediation:** `NUMERIC(14,2)` (and `NUMERIC(14,4)` for rates) end-to-end, integer minor units at boundaries, golden-case tests, explicit rounding policy.

### H-9 — No background job execution
**Severity: High**  
**Evidence:** leave accrual (`app/main.py:671`), backups (`1407`), migrations (`1445`), retention (`1577`) execute synchronously inside HTTP requests.  
**Impact:** request timeouts, partial state on failure, no retry/idempotency, no scheduled execution.  
**Remediation:** queue + worker (Dramatiq/Celery/RQ on Redis or PostgreSQL-backed), idempotency keys, job status API, scheduler.

### H-10 — Deployment is a development server
**Severity: High**  
**Evidence:** `Dockerfile` runs `python run.py` → `uvicorn.run(...)`; no Gunicorn, no non-root user, no healthcheck, no resource limits; `docker-compose.yml` exposes `8090` directly with no TLS; `PEAWORK_SECRET` defaults to `replace-before-production`.  
**Impact:** single process, no TLS, root container, no restart policy, no backup service.  
**Remediation:** Gunicorn + Uvicorn workers, non-root, Caddy TLS reverse proxy, PostgreSQL, healthchecks, resource limits, scheduled `pg_dump` with restore verification, systemd alternative.

### M-1 — Audit log is mutable and incomplete
**Severity: Medium**  
**Evidence:** `audit_log` is a normal table (`app/db.py:70`); entries are written as part of the same transaction; `details` often contains free text and potentially PII; no hash chain, no retention policy enforcement on audit, no central shipping.  
**Remediation:** append-only audit table, restricted DB role (no UPDATE/DELETE), hash chain or WORM export, structured event schema, redaction, retention + archive. Do not log sensitive field values.

### M-2 — Upload pipeline stores files but does not serve them safely
**Severity: Medium**  
**Evidence:** `app/storage.py` validates extension/MIME/size and optionally ClamAV; local files are written under `uploads/` with a predictable key. No download route with authorization was found in the audited surface; files may be served by the reverse proxy if misconfigured. Content is not encrypted at rest; no checksum, no retention linkage.  
**Remediation:** private object storage (MinIO/S3) or a non-web-served directory, authenticated download endpoint with object-level authz, content-disposition, checksum, encryption at rest, AV quarantine bucket, presigned short-lived URLs.

### M-3 — Observability is shallow
**Severity: Medium**  
**Evidence:** `/health` and `/metrics` are unauthenticated; metrics are hand-built text; no structured request logs, correlation IDs, latency histograms, error tracking, or alerting rules.  
**Remediation:** JSON logs with request IDs, Prometheus client metrics, `/health/live` + `/health/ready`, optional OpenTelemetry, Grafana dashboards, alert rules. Keep `/metrics` internal-only.

### M-4 — Tests are one integration file, order-dependent
**Severity: Medium**  
**Evidence:** `tests/test_app.py` (410 lines) mutates a shared SQLite file; assertions depend on `MAX(id)` and seed ordering; no unit tests for payroll or authorization; no coverage gate; no CI config.  
**Remediation:** test pyramid (unit for domain rules, integration for API, Playwright for critical journeys), isolated DB per test, factories, coverage floor, CI matrix.

### M-5 — Accessibility and i18n claims outrun implementation
**Severity: Medium**  
**Evidence:** English/Hindi translation helper (`app/i18n.py`, 1 KB); many templates use raw tables and inline styles; CSP allows `'unsafe-inline'`; no automated axe checks in CI.  
**Remediation:** semantic HTML, focus management, WCAG 2.2 AA audit, axe-core in CI, gettext/Babel, locale-aware dates/numbers/currency, RTL readiness.

### M-6 — No API contract discipline
**Severity: Medium**  
**Evidence:** API routes return raw `sqlite3.Row`/dict rows; no Pydantic response models, no pagination, no filtering contract, no idempotency, no deprecation policy, no OpenAPI examples.  
**Remediation:** Pydantic schemas, cursor pagination, RFC 9457 problem details, versioned `/api/v1`, OpenAPI snapshot tests, API keys with scoped permissions.

### M-7 — PII handling and privacy gaps
**Severity: Medium**  
**Evidence:** PAN/bank only "masked" in column names; free-text audit details; no field-level encryption; retention jobs exist but run synchronously; no DSAR export package; no consent/purpose registry.  
**Remediation:** classify data, encrypt sensitive fields (application-level envelope encryption or pgcrypto with KMS), redact logs, DSAR export/erase jobs, consent and purpose records, DPIA template.

### L-1 — Documentation includes unsupported version claims
`test_health` expects `1.0.0` while app reports `1.2.0`; roadmap ordering lists v1.2 before v1.1. Low risk but signals weak release discipline.

### L-2 — Repository hygiene
No `.gitignore` audit shown for `data/`, `uploads/`, `.venv/`; generated DBs and uploads could be committed. Add `.dockerignore`, `.gitignore`, secret scanning, and branch protection.

## 4. What is genuinely good (keep it)

1. **Domain decomposition is thoughtful.** Effective-dated assignments, lifecycle events, approval-gated transfers, separation of payroll preview vs finalization, and evidence-gated readiness are sound HR domain concepts.
2. **Fail-closed instincts exist.** Statutory rules cannot finalize unvalidated; malware scanning can be required; readiness gates block on open high/critical events.
3. **India-first scope is clear.** DPDP, PF/ESI/TDS boundaries, and the "not filing-ready" caveat are honest.
4. **Explicit non-certification language.** The README/docs do not pretend to be certified.
5. **Broad acceptance criteria.** The PRD is a strong basis for automated tests in the successor.

## 6. Go/No-Go criteria for a limited Linux pilot

A pilot may start only when **all** are true:

- [ ] PostgreSQL is the only production datastore; migrations applied by CI/CD.
- [ ] Object-level authorization tests pass for employee, manager, HR, admin.
- [ ] No default credentials; first-boot secret generation verified.
- [ ] TLS via reverse proxy; secure/HttpOnly/SameSite cookies; HSTS.
- [ ] Every write is CSRF-protected; login throttling verified.
- [ ] Audit events are append-only and reviewed for PII.
- [ ] Backup + restore rehearsal with measured RPO/RTO.
- [ ] Dependency scan clean of critical/high CVEs.
- [ ] UAT sign-off on employee, leave, org, document flows.
- [ ] Documented incident and rollback procedure.

Payroll remains **out of scope** for the first pilot until R3 sign-off.
